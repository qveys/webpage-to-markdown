# Plan de test de non-regression

> **Issue** : QUE-123
> **Auteur** : CTO
> **Date** : 2026-06-18
> **Scope** : extension Chrome MV3 `Webpage to Markdown` v1.0.1

## Resume executif

Le risque principal du projet est un refactor sur `src/popup/popup.js` qui casserait silencieusement l'extraction, la conversion Markdown ou les actions utilisateur du popup. Le filet de securite recommande est volontairement simple :

1. une checklist manuelle courte pour chaque PR touchant l'extension ;
2. des tests unitaires sur la logique pure qui ne depend pas des APIs Chrome ;
3. plus tard, une couche e2e sur extension chargee manuellement, mais hors perimetre de cette issue.

## Recommendation de framework

**Framework recommande : Vitest**

Justification :

- compatible nativement avec le mode ESM deja active dans `package.json`
- demarrage plus leger que Jest pour un petit projet vanilla JS
- API de test proche de Jest, donc faible cout d'adoption
- permet d'ajouter plus tard `jsdom` ou des mocks ciblés sans changer d'outil

Decision de triage :

- **Vitest maintenant** pour couvrir la logique pure
- **pas d'e2e Chrome dans cette issue**
- **pas de mocking lourd de `chrome.*` tant que le code n'est pas davantage decoupe**

## Checklist manuelle reutilisable par PR

Utiliser cette checklist pour toute PR touchant `manifest.json`, `src/popup/*` ou la logique de conversion.

| ID | Scenario | Etapes | Resultat attendu | Critique |
|---|---|---|---|---|
| M1 | Conversion standard d'un article | Charger l'extension, ouvrir une page article, cliquer `Convert Page to Markdown` | Le textarea contient un markdown non vide avec le titre en tete | Oui |
| M2 | Page sans `main` ou `article` | Ouvrir une page simple sans conteneur semantique principal, convertir | Le fallback sur `body` produit quand meme du contenu | Oui |
| M3 | Page avec iframes accessibles | Ouvrir une page avec iframe same-origin, convertir | La section `Embedded Content` apparait dans le markdown | Moyen |
| M4 | URL restreinte | Ouvrir `chrome://extensions` puis le popup | La conversion est refusee avec un message d'erreur, sans casser le popup | Oui |
| M5 | Option frontmatter | Activer `Include Frontmatter`, convertir une page | Le markdown commence par `---` avec `title`, `url`, `date` | Oui |
| M6 | Variation du style de titres | Basculer `Heading Style` entre `ATX` et `Setext` puis convertir | Le rendu markdown change conformement au reglage | Moyen |
| M7 | Variation du marqueur de liste | Changer `Bullet Style`, convertir une page contenant des listes | Le marqueur `-`, `*` ou `+` est respecte | Moyen |
| M8 | Variation du style de blocs de code | Changer `Code Block Style`, convertir une page contenant du code | Le rendu passe de fenced a indented selon le reglage | Moyen |
| M9 | Copie presse-papier | Apres conversion, cliquer `Copy` | Le contenu converti est copie et le toast de succes apparait | Oui |
| M10 | Telechargement fichier | Apres conversion, cliquer `Download` | Un fichier `page-YYYY-MM-DD-HH-MM-SS.md` est telecharge | Oui |
| M11 | Persistance du theme | Basculer clair/sombre, fermer et rouvrir le popup | Le theme choisi est conserve | Faible |
| M12 | Persistance des reglages | Modifier frontmatter/titres/listes/code, fermer et rouvrir | Les reglages restent synchronises avec l'UI | Moyen |
| M13 | Erreur d'onglet actif | Fermer rapidement l'onglet ou cibler un cas invalide pendant la conversion | Le popup reste stable, `Copy` et `Download` restent desactives | Oui |
| M14 | Conversion apres erreur | Provoquer une erreur puis convertir une page valide | Une conversion suivante redevient possible sans recharger l'extension | Oui |

## Scenarios automatisables maintenant

Les cas suivants sont automatisables sans navigateur reel ni mocks Chrome lourds :

| ID | Scenario automatisable | Cible |
|---|---|---|
| A1 | Detection des URLs interdites | fonction pure `isRestrictedUrl()` |
| A2 | Normalisation des sauts de ligne | fonction pure `normalizeMarkdown()` |
| A3 | Construction du frontmatter | fonction pure `buildFrontmatter()` |
| A4 | Nommage deterministe du fichier telecharge | fonction pure `buildDownloadFilename()` |

## Scenarios automatisables apres leger refactor

Ces cas deviennent raisonnables des que l'extraction ou les dependances DOM/Chrome sont injectables :

| ID | Scenario cible | Strategie |
|---|---|---|
| B1 | Activation/desactivation des boutons `Copy` et `Download` | test DOM sur popup avec `jsdom` |
| B2 | Gestion des erreurs de `chrome.tabs.query()` ou `chrome.scripting.executeScript()` | mocks ciblés des APIs Chrome |
| B3 | Respect des options Turndown | test integration leger sur HTML fixe + service configure |
| B4 | Presence de la section `Embedded Content` | test d'assemblage sur contenu extrait mocke |

## Couverture minimale exigee avant refactor important

Avant toute evolution structurelle type service worker, Readability ou modularisation plus profonde, exiger au minimum :

- passage de `npm test`
- execution manuelle de M1, M4, M5, M9 et M10
- verification que `manifest.json` n'ajoute pas de permission sans justification explicite

## Evidence laissee par cette issue

- Ajout de `npm test` avec Vitest
- Ajout de tests unitaires sur la logique pure extraite du popup
- Extraction minimale de helpers purs pour stabiliser les regressions les plus probables
